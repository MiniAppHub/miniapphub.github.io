Документация

Всё, что нужно, чтобы написать мини-приложение, опубликовать его в каталоге и работать с оболочкой MiniAppHub.

Введение

MiniAppHub — платформа для HTML5 мини-приложений. Приложение — это обычный статический сайт плюс файл манифеста. Оболочка (Android или Windows) показывает приложение в изолированном iframe и даёт ему доступ к системным возможностям через мост сообщений.

У оболочки нет собственного интерфейса. Единственное, что она делает, — открывает мини-приложение, назначенное лаунчером. По умолчанию это miniapphub.home: рабочий стол, каталог и настройки.

Никаких сборщиков и транспиляции. Файлы отдаются как есть, код пишется в ES-модулях, документация — через JSDoc.

Анатомия приложения

mapp/
  mapp.manifest.json     манифест: id, версия, права, роутеры
  public/
    index.html           точка входа интерфейса
    app.js               логика, ES-модуль
    api/
      sdk.js             клиент моста
      qr.js              фоновое API для других приложений

Каталог public/ публикуется на GitHub Pages как есть. Роутеры в манифесте позволяют держать разные точки входа для клиента, веба и превью.

Манифест

{
  "id": "headmad.qr-tools",          // author.app-name, ставится автоматически
  "name": "qr-tools",
  "version": "1.0.0",               // семвер, должен совпадать с тегом vX.Y.Z
  "author": "headmad",                // GitHub-логин
  "description": "Генератор QR-кодов",
  "icon": "public/assets/icon.svg",
  "permissions": ["apps.manage"],
  "dependencies": [],
  "routers": { "app": "public", "web": "public" }
}
ПолеНазначение
idУникальный идентификатор author.name. Префикс обязан совпадать с author.
versionСемантическая версия. Обновление в каталоге происходит при смене версии.
iconПуть внутри mapp/. SVG или PNG.
permissionsЗапрашиваемые разрешения. Пользователь видит их при установке.
dependenciesid приложений, чьё public/api/ нужно для работы.
routersТочки входа: app, client, web, preview.

Публикация

Порядок повторяет механизм Fork + Pull Request:

  1. Fork репозитория MiniAppHub/template.
  2. Правка кода в mapp/ и версии в манифесте.
  3. Pull Request — CI проверяет манифест и совпадение автора.
  4. Тег vX.Y.Z — собирается архив mapp/, создаётся GitHub Release, обновляется ветка gh-pages.
  5. Портал забирает релиз и обновляет запись в catalog.json.
Смена только patch или minor перезаписывает релиз latest. Смена major выпускает отдельный релиз с полным архивом.

Как работает мост

Приложение не имеет прямого доступа к оболочке. Вместо этого оно отправляет сообщение из своего iframe и ждёт ответа:

// приложение → оболочка
{ source: 'mapp', id: 7, namespace: 'shell', action: 'getSettings', params: {} }

// оболочка → приложение
{ source: 'mapp-shell', id: 7, response: { ok: true, result: { … } } }

Оболочка принимает сообщения только из своего iframe. Ответ всегда имеет форму { ok: true, result } либо { ok: false, error }.

Внутри оболочки действие подгружается динамически — import('./api/shell/getSettings.js') — и вызывается его экспорт по умолчанию. Один файл содержит ровно одно действие.

import { mapp } from './api/sdk.js';

const res = await mapp.shell('getSettings');
if (!res.ok) console.error(res.error);
else console.log(res.result.theme);

shell.*

ДействиеПараметрыРезультат
shell('getSettings')— { catalogUrl, launcher, theme }
shell('setSettings') { catalogUrl?, launcher?, theme? } Обновлённые настройки. Проверяются схема URL и значение темы
shell('getVersion')— { version, platform, api }
shell('openApp'){ id } Открывает приложение вместо текущего. Нужно shell.launcher
shell('closeApp')— Возвращает управление лаунчеру
shell('setLauncher'){ id } или { id: null } Назначает лаунчер. Нужно shell.launcher
await mapp.shell('setSettings', { theme: 'light' });
await mapp.shell('openApp', { id: 'headmad.qr-tools' });

apps.*

ДействиеПараметрыРезультат
apps('getInstalled')— Массив { id, name, version, url, permissions, icon }
apps('installApp'){ id } или { manifestUrl } Запись установленного приложения. Нужно apps.manage
apps('uninstallApp'){ id } { id }. Нужно apps.manage

Установка по id берёт адрес из catalog.json. Установка по manifestUrl читает манифест напрямую — так работают экспериментальные сборки, которых нет в каталоге.

system.*

ДействиеПараметрыРезультат
system('getInfo')— { platform, shell, language, online, time }. Платформа может добавить поля
system('share'){ title, text, url } { shared, copied }. Без Web Share копирует в буфер

Проверка выполняется на стороне оболочки: без разрешения в манифесте действие вернёт { ok: false, error: 'permission denied: …' }.

Свои действия в оболочке

Оболочка ищет реализацию сначала в своём каталоге api/<namespace>/<action>.js, затем в ядре core/api/<namespace>/<action>.js. Поэтому платформа переопределяет поведение, не меняя ядро.

// api/system/getInfo.js — переопределение для Windows
export default async function getInfo() {
  return { platform: 'windows', webview: 'tauri' };
}

Имя действия ограничено шаблоном [a-z][a-zA-Z0-9], подстановка пути невозможна.

Лаунчер и первый запуск

При старте оболочка читает config.json из собственной сборки:

{ "launcher": "miniapphub.home", "catalogUrl": "https://miniapphub.github.io/catalog.json" }

Значение launcher приходит из переменной репозитория LAUNCHER_APP и попадает в сборку на этапе CI — менять его можно без правки кода. Дальше:

  1. Оболочка проверяет, установлен ли лаунчер, и при необходимости ставит его из каталога.
  2. Лаунчер открывается в песочнице и рисует интерфейс.
  3. Пользователь может сменить лаунчер: приложение с разрешением shell.launcher вызывает setLauncher.

Если каталог недоступен, используется launcherUrl — прямой адрес лаунчера на GitHub Pages.
